# Work order — v1.6.3

Director's order of work for this build. Priority is decided here; a lower number outranks a
higher one when two items compete for the same hours.

**Scope ruling for this build: no OCR work.** The order below contains none. Existing OCR stays
exactly as shipped — ML Kit on device, the searchable-PDF text layer, `ocr_text`/`ocr_lines` on
the page row, search over them in `LibraryScreen`. Nothing is removed. If "we don't need OCR"
meant *strip it out*, that is a different and larger change (schema, export, search) and it needs
to be said explicitly.

## P0 — UI stability

"Stable" is defined here as: **nothing on screen moves unless the user moved it, and no control
silently undoes the user's work.** Four items, each with a way to check it.

### P0.1 The preview outline moves while the scene is still

Owner-felt and measured. In the 149-frame recording of the reported jump (`/tmp/opencode/jump.mp4`,
720×1280): the scene itself moves a **median of 0 px per frame**, yet the outline's edges move a
median of **5**, p75 **11**, p90 **26** recording px — up to ~49 screen px in one frame — and the
teal stroke is present in only **81 of 149** frames. So it is not only a tween artefact: the
outline is being *lost and re-found* while nothing moves.

Acceptance: scene motion 0 px/frame ⇒ outline edge motion ≤ 2 screen px/frame, and the outline
present in ≥ 95 % of frames.

Two halves, and they are separable:

* **Pacing** — done. `DEFAULT_INTERVAL_MILLIS = 100`, `DEFAULT_TWEEN_MILLIS = 180`
  (`core/imaging/OutlineTracker.kt`), committed in `7a6e4a0`, evidence in
  `docs/specs/document-framing/design.md` §1. The 180 ms tween is longer than the detection gap, so
  the outline glides instead of stepping — the competing scanner's relation.
* **Detector stability** — done, in the same commit as the outcome below. The accepted quad in the
  recording spans nearly the whole preview with its left and right edges pinned at the frame
  border: the detector ranks two descriptions of the same still page — a loose one around the sheet
  and one clamped to the frame — and the ranking swaps between frames. Following whoever came first
  dragged the outline across the frame; the frames where only the rival survived lost the stroke
  entirely. So the edge stage now reports its whole shortlist (`DocDetector.candidates`, head equal
  to `detect`), and `OutlineChooser` weighs it against the outline already on screen, in units of
  that outline's own span. A candidate elsewhere is evidence that a page is in view, not news about
  where: it holds the border and refreshes the hold, and is believed only after the *same*
  description has been offered for the full `holdMillis` — the swap never qualifies, because its two
  descriptions are not the same one. `OutlineStabilityTest` plays back the measured sequence and
  holds the acceptance figures above; the displacement reachable by a re-aim is
  `OutlineTrackerTest`'s four disagreement cases.

Owner: Director (diagnosis, recording, acceptance), developer for the fix once diagnosed.
Size: M. Device check still outstanding: the playback proves what the tracker does with the
measured sequence, not that the detector stops preferring the clamped quad on a real phone.

### P0.2 Detect must not throw away the user's rotation

`EditorViewModel.runAutoPass()` assigns `rotation = prepared.plan.rotationDegrees`
(`ui/EditorViewModel.kt:194`) unconditionally, while `rotateQuarter()` has just set the user's own
rotation (`:238`). Press **Detect** after turning a page upright by hand and the page is re-planned
from the untouched original and turned back. A control labelled "detect" that silently reverses a
rotation is the worst kind of instability: it looks like a bug in the scan.

Acceptance: with a manual rotation of 90/180/270 applied, Detect re-finds the outline and keeps the
page exactly as the user turned it; the outline lands on the same physical edges, not on a
re-planned frame. Covered by a JVM test on the quad-rotation arithmetic (core imaging), not only by
eye.

Owner: developer. Size: S–M (the frame-to-frame rotation of the quad moves into `core/imaging` so it
can be tested).

### P0.3 Batch says nothing to TalkBack

`grep -rn 'stateDescription' app/src/main/java` returns nothing: the Batch chip
(`ui/camera/CameraScreen.kt:433`) is a toggle with no state exposed, so it reads the same whether
the run continues or not. A control whose state is invisible is unstable for anyone not reading the
colour.

Acceptance: Batch announces on/off; the mode chips announce the selected shape. No behaviour change.

Owner: developer. Size: S.

### P0.4 The strip must not jump when a Book shot yields one page instead of two

New, introduced by the book fix itself. `spreadPages()` will now commit one page or two depending
on the shot. If the strip or the page counter assumes two, the UI will flicker between counts.

Acceptance: a Book capture of a single page adds one tile; a spread adds two; the counter, the
review's page list and the re-take affordance all agree in both cases.

Owner: developer (inside the book-mode change). Size: S.

## P2 — Book scanning, made genuinely better

Only after P1 is accepted. Ranked, not committed:

1. **The stuck seam** — the guide is at the geometric centre, but `Spread.findSeam` finds the
   darkest column. On a spread whose gutter is off centre the guide and the cut disagree. Making
   the guide follow the detected seam would be the honest affordance.
2. **Auto-capture on page turn** — the competing scanner's signature feature, and a native
   nine-point/nine-class classifier (`PageScanner.DetectTurnPage`, `nativelib/PageScanner.java:76`;
   `doCapture() = detectResult == 1`). Awaiting the owner's decision: behind a toggle with a settle
   gate, or left out. A heuristic stand-in fires mid-turn.
3. **Curvature-aware dewarp and model-based deshadow** — their `DetectCurveBorder` /
   `SplineFitAdjustCurves` / `deshadowImagePtr2`. Out of scope for this build; recorded.

## Not in this build

* **OCR**: no additions (scope ruling), no removals.
* **PDF tools** — page numbers, text watermark, merge, extract, export compression, password,
  signature. Evidence and ranking in `docs/specs/app-survey/survey.md` §2–4. Deferred to the next
  build, with the reasoning: stamps are cheap and testable, password is not cheap at all.
* **PDF → Word/Excel/PPT**: server-backed in the competing app, not reproducible offline.
* **Multilingual OCR**: needs a model artifact the offline Gradle cache cannot supply.
* Previously carried: folder rename/bulk rename, dark-mode status-icon mismatch, radii/padding taste,
  TalkBack crop canvas, dead-code removal, CamScanner's amber out-of-frame colour.

## Sequencing, and why

P0.1 was the only item blocked on the owner, and the recording that unblocked it has been taken and
measured; P0.2/P0.3/P0.4 and P1 verification proceed now, and P2 starts only when P1 is accepted,
which keeps one book change in review at a time.

One build tree, one Gradle daemon: only one developer agent runs tests at a time. That is why the
next feature is queued rather than dispatched alongside the book-mode work.
